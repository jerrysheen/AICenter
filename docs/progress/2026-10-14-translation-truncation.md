## 1. 已保存的截断译文

`x:2110120766247424458` 的译文停在「…缺乏公开信息（我...」，原文有两段。补译没有重排，是因为过短判断要求正文至少 600 字，这条更短，哈希又对得上，被当成已经译完。

不是输出 token 上限。Gemma 单次 `maxOutputTokens` 是 4096，`finishReason` 不是 `STOP`（包括 `MAX_TOKENS`）时整段丢掉，不落库。两段短帖到不了这个上限。短帖走批量翻译，模型以 `STOP` 返回时，只要 JSON 能解析就保存。单条翻译只在原文不少于 400 字时检查长度。省略号、未闭合括号或没有句末标点，都会被存下来。

现在用译文和原文的长度比，并看结尾。拉丁原文译成中文通常可以短到大约四分之一；汉字原文要更接近原文长度。不足 80 字的短帖不用长度比。结尾是 `...` / `…`、括号没闭上，或原文有句号而译文没有，也算截断。原文自己以省略号结束、长度又正常时，不因此重译。启动补译仍最多 80 条、同时最多 2 条，会读译文末尾 240 字，命中的重新入队。

保存前用同一套判断。批量结果被截断时改走单条，并再试，不把截断译文写入缓存。提示语写明不要自行用省略号或未闭合括号结束。

新译文写好之前，阅读页如果已有完整的中文 `normalizedArticle`，先显示那一篇，不显示截断译文。

## 2. 预览接在全文前面，全文在句中停下

时间线预览以 `…` 结尾时，全文并不包含这串预览，于是预览被接在全文前面，第一句出现两次。长文读到 400 字就停，标题再接到正文前，所以会停在「飞行器」这种半句上。

全文已经覆盖预览或标题时，不再把预览或标题接在前面。长文继续读到字数稳定，中间会滚动页面，不再以 400 字为停止线。入库和推文整理用同一条规则去掉前导预览。启动补译扫到仍带这段预览的正文时，改掉正文并重新入队；库里没有的后半段要等下次抓到这条长文。抓取不再提前停下之后，后半段才会进来。

## 3. 每次加载都有一条 translations 400

手机每次打开 X 列表都会 `POST /api/v1/feed/translations`。列表没有正文，也没有 `translation.text`，只有标题和摘要。本地缓存按空正文做键，于是带上 `sourceText: ""`。这个字段必填，校验失败就是 400。没有正文的条目不再上传；id 超过 128 字的也不上传。有正文的本地译文仍会同步。

需要同时重启 Web 和 Worker。浏览器再加载一次。不要重建数据库。
