# 媒体页远程读取延迟

## 目标

用户反馈公网打开信息流媒体页约需5–6秒。改善首批内容传输和再次打开的显示时间，保留现有Service、Repository、Contract、Worker和设备授权边界。

## 决定与改动

- 现状：服务端媒体读取仅访问已落库内容。本机读取科技全文列表约0.1秒，初次观测37篇响应638,908字节，未压缩；客户端仍等待第二次标签读取后才渲染，没有持久化媒体显示缓存。
- 媒体页首批使用已有分页Contract读取12篇，滚动时追加并去重；刷新覆盖当前已加载范围，切换栏目丢弃晚到响应，重复请求合并。
- 使用Feed中已有tags立即渲染，标签字典异步读取。恢复媒体页时先加载媒体，其他社媒/灵感/任务数据稍后读取，不并发请求总览的全套行情和日程。
- 新增设备端显示缓存：同源、按设备身份隔离；授权成功后才能显示，后台每次对齐服务器，退出/检测到授权失效时清除。仅保存各栏目首批12篇，最多6份、合计1,000,000字符、24小时；存储失败不阻塞页面。阅读文章时更新缓存中的已读状态，保留已有文章且不延长缓存寿命。SQLite继续作为业务真源。
- 媒体Feed接口协商gzip，保持no-store，不改变其他JSON接口或设备Cookie/SSE。
- 稳定说明同步到architecture；没有迁移、数据库重建、外部源抓取策略或Agent变更。

## 验证

- 专项测试覆盖缓存先显示、未授权不显示、分页与去重、重复请求合并、栏目切换、失败保留内容、注销/撤销清缓存、晚到响应、过期/配额/设备隔离、实际媒体HTTPgzip和静态模块交付。
- 后续实测同一已存列表：37篇完整响应642,461字节；12篇136,064字节，gzip后37,116字节。相对旧完整未压缩响应减少约94%。数据持续更新，字节数不是固定基准。
- `npm run check`通过：syntax/source/harness、Contract类型检查、架构、Harmony与633项测试全部通过；新增浏览器模块另行`node --check`通过，`git diff --check`通过。
- 运行服务已核对新模块交付：本机与公网`media-feed.js`均200且包含加载器。真实HTTP原始字节核对：37篇gzip为171,727字节，12篇gzip为37,113字节；`Content-Encoding: gzip`、`Cache-Control: no-store`均正确。核对时保留运行中的`media.index.enrich`任务，没有从本会话发起重启。

## 范围与限制

手机移动网络的最终加载耗时需要用户实际复核；没有把本机请求耗时当作手机实测。缓存首次产生前仍需要联网下载。对正在运行的后台任务保持保护，不为了HTTP压缩直接中断Worker。

## 媒体页顶部简化

用户随后要求顶部只保留「宏观与国际 / 科技产业」。移除正文状态分类、数量/读取说明、立即更新、来源与自动更新、检查连接按钮及其样式；媒体栏目下隐藏通用筛选按钮、数量与日程入口。沿用默认全文视图，不再恢复旧的摘要/处理中分类选择。后台采集、翻译、标签、分页和设备缓存继续运行。仅修改页面，静态资源指纹更新后生效，无需重启服务。
