# 豆包翻译等待、一次失败即返回与发消息队列

## 目标

豆包页面上译文已经生成时，本地不要再空等；一次挂起就结束请求，让用户再点翻译。本进程内发给豆包的消息走同一条队列。

## 现象

同一对话里 12:47 与 12:48 两条信封的 `batch_id` 不同（`...462528` 七条、`...512950` 十四条），间隔约 50 秒。这是一次「翻译」被 `packFeedAiBatches` 按 5000 字拆成两次豆包发送，不是同一任务失败重发。

慢的原因：等待逻辑要等流式结束且文本不再增长，JSON 已经完整时仍可能因为 `data-streaming` 或 Markdown 继续变化而拖到上限；第一批发完再发第二批，再叠加 Gemini / 单条引擎，请求会一直占着。

## 决定

- 翻译一次最多 30 条，打成一封豆包信封；条目仍可截到约 5000 字。
- 固定 JSON 的全部 id 一出现就结束等待；读不到时只刷新当前对话一次，不重发。
- 发给豆包的正文经分块 `evaluate` 写入。一整封 JSONL 塞进一次 `bsk evaluate` 会触发 Windows「文件名太长」，CLI 空返回，页面就显示 `bsk did not return valid JSON`。
- 豆包挂起 / 超时：HTTP 失败返回，页面提示再点一次。同一次请求不改走 Gemini，也不逐条翻译。
- 本进程 `DoubaoAskQueue`：翻译、CLI 与后续 API 都 `enqueue`，一次只发一条并回收回复。不是 Worker Job，也不是 Agent Tool。后到的请求排队等待，不并行抢同一个豆包页。

## 验证

`npm run check`。
