## 0. 补译不再占满翻译席

翻译并发默认仍是 5。启动补译同时最多 2 条，可用 `AI_CENTER_TRANSLATION_BACKFILL_CONCURRENCY` 设为 1 或 2。并发至少为 2 时，这个上限再减一席，留给优先级大于等于 0 的任务。手机发起的翻译是 10，入库触发的翻译是 0，启动补译是 -10。已经在排队、优先级还是 0 的补译任务，下次启动补译会改成 -10。

补译在配额窗口里最多等 4 次，每次最多约 70 秒，等待期间席位不放。分段重试也在同一条任务里，同样占着补译份额。等满或被中止后才按原来的失败路径重试。优先级大于等于 0 的任务碰到配额窗口仍立刻失败并让出席位。Worker 启动时写一行 `[worker] translation-slots limit=… backfillCap=…`。

## 1. 小时报展开用译文，栏仍按入库

小时栏按首次入库归窗：社交用内容条目的 `createdAt`，不是 `publishedAt`。行上的钟点是原文发布时间；没有发布时间才用入库时间。发布在 02:53、入库落在 12:00–13:00 的帖，出现在那一栏、行上显示 02:53，两处都按这个规则，这次不改归属。

展开后的正文优先用内容条目的 `translation.text`。没有译文时才用信息节点里的原文。

## 2. 社媒按上海发布日分组

分组键和行上钟点用同一个时刻，时区是 Asia/Shanghai。非官方条目只要 `publishedAt` 不晚于现在 48 小时，就用发布时间，不再因为几分钟的时钟偏差改用入库日。官方未来生效日仍按收录时间。

X 的状态 id 是雪花时间。页面上的时间若和它相差超过 36 小时（常见于引用帖的时间），写入 `publishedAt` 时改用雪花时间。短 id 不用这规则。正文哈希没变、只是时间差超过 36 小时时，更新 `publishedAt`，不改 `captured_at`。已经写错的行要等这条帖再次被看到才会改。

## 3. 社媒条数以第一页为准

非翻页的加载用服务端这一页替换本地列表，不再把上一轮多出来的尾巴留着。同一条若已经展开，正文和译文仍留在新的一页里。重点页的已保存窗口只在「重点」里往列表上合并；离开重点后再进社媒或全部，会重新拉第一页。两次替换请求重叠时，后发起的那次写入。

列表顺序仍是首次 `captured_at`。正文再变时不再把 `captured_at` 改成这一批的时间，所以第一页不会因为评论或正文更新被重新洗牌。已经被改写过的 `captured_at` 不会自动还原。iHerb、Kingsley W 若只出现在客户端拼出来的后页里，重新加载后只在第一页按首次收录时间还排得到时继续显示，不是被删掉。

## 4. 截断译文、重复首句和 `x:` id

长正文配上过短的译文会重新入队：正文至少 600 字，译文短于 120 字，或译文不足正文的五分之一，且没有达到「160 字且不少于四分之一」。列表卡片标题仍是译文第一句，最多 80 字，超出显示省略号；全文在 `translation.text`。一段译文明显短于原文时先重试，再保存。

相邻两段如果后一段用前一段的首句开头，或有至少 12 字的前后重叠，拼接时去掉重复。阅读页看到已保存的重复首句时也会去掉一次。

`GET /api/v1/content-items/x:…`、`xueqiu:`、`bilibili:`、`trendforce:` 按 `provider:externalId` 读取。只读令牌允许这种路径。状态补丁仍只接受内容条目的 UUID。
