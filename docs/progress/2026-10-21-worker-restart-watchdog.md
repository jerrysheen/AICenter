# Worker 不再因调度失败自己退出

## 原因

07:00、10:36–10:49、13:21、14:36–14:47 这几段里，Worker 进程退出后由启动器再拉起。新进程看到旧 pid 已经不在，把当时还在跑的任务收成 `WorkerLeaseExpired`。

Node 22 遇到没有接住的 Promise 拒绝会直接退出。调度循环 `scheduler.start()` 没有人等待。某一条定时任务入队时如果抛错（数据库正被占用、入队校验失败），这个拒绝就是没人接的。进程退出，启动器只重启 Worker。失败的那条调度往往还停在原来的下次时间，新进程马上又入队、又退出，于是出现十几分钟的一串重启。单次的 07:00 和 13:21 是同一种退出，下一轮入队成功了，所以只重启一次。

任务循环的看门狗只在事件循环还能跑时记一行，而且不写当时在跑的任务。主线程看门狗的工作线程一旦把消息发不回去，`error` 没有监听，同样会把整个进程打退出。

## 决定

调度每一条单独接住错误，记下调度键和错误，继续后面的条目，循环也不退出。Worker 进程再装一个未处理拒绝的监听，只记日志，不退出。启动时真正抛出的错误仍按原来的方式结束进程。

任务循环看门狗的那一行带上正在跑的任务。主线程看门狗在回复和工作线程发消息时接住克隆失败和已退出的线程，并监听 `error`，避免看门狗自己把 Worker 打退出。

不新增 migration。当前 schema 是 95。下一号是 96。空号仍是 63、79、80、82。不要重建数据库。

需要重启 Worker。页面没有改，Web 不用为这项重启。
